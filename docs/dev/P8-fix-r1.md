# P8 S2 수정 지시 — 1회차 (Claude 중간 2·낮음 3, OpenAI 높음 2·중간 2·낮음 1)

규칙 동일(커밋·docs·프롬프트 수정·키 출력 금지, 실제 수집·LLM 실행 금지).

## 높음
1. **수집 실패 날도 완료 처리** (양쪽 지적) — 출처별로 수집 성공 여부를 기록한다. 수집 캐시는 **성공한 출처만** 저장하고(`collected/<날짜>.json`에 출처별 `ok` 표시), 실패한 출처는 다음 실행에서 그 출처만 다시 수집한다. **모든 출처가 성공한 날만** 분류·결과 파일 확정. 실패 출처가 남은 날은 미완료로 콘솔·요약에 표시(`--yes` 실행에서도 그날은 분류하지 않음). dry-run에서도 실패 출처는 캐시하지 않는다. 테스트: GitHub 실패 → 다음 실행에서 GitHub만 재수집, HN은 캐시 재사용, 결과 파일 없음 → 이후 성공 시 확정.
2. **예산 중단 후 재분류 비용 반복** (OpenAI 높음, Claude 낮음) — 날짜별로 분류에 성공한 항목을 `interrupted/<날짜>.json`에 누적 저장하고, 재실행 시 **성공한 항목은 재사용하고 남은 항목만** 분류한다. 그날 모두 끝나면 합쳐 결과 확정, interrupted 파일 삭제. 비용은 누적 합계로 기록. 테스트: 2묶음 중 1묶음 성공 후 차단 → 재실행 시 분류 요청은 남은 1묶음만.

## 중간
3. **집계 기준 차이로 증가율 부풀림** (Claude 중간 1) — 실제 실행에서는 GitHub 저장소가 생성 후 14일 동안 매일 다시 잡혀(재등장) 주마다 세어지고, 채운 날은 생성일 한 번만 센다. **결정: (a)** 비교 기간에 채운 날이 섞이면(출처 맞춤 모드), 증가율·◆·시장 급증 계산은 **모든 주에서 HN·GitHub의 새 분류 관측만**(재등장 제외, 실제 실행 날도 같은 기준) 쓴다. 표시는 `HN·GH 새 항목 기준`. 표의 건수 칸은 전체 그대로. 테스트: 실제 실행 주에 재등장이 많고 새 항목은 비슷할 때 거짓 ◆ 없음.
   - ◆의 **출처 조건(≥2)은 이번 주 전체 관측**(모든 출처) 기준으로 센다 — 출처 맞춤 모드에서 HN·GitHub 둘 다에 나와야만 ◆가 되는 문제 해결(Claude 낮음). 테스트.
4. **실제 실행 날의 채운 분류가 재등장 색인에 섞임** (OpenAI) — 재등장 원본 색인에서, 그날 실제 실행이 있는 날짜의 backfill 분류는 **제외**. 테스트.
5. **SourceCap 순서** (OpenAI) — 정제 순서를 일일 파이프라인(Pipeline.kt)과 같게(SourceCap을 중복 제거 앞). 가능하면 일일 파이프라인의 정제 함수를 공용으로 빼서 seen 단계만 건너뛰게 한다. 테스트: 같은 입력에서 seen 제외 정제 결과가 일일과 동일.
