# R2 수정 지시 — 2회차 (OpenAI 높음 3·중간 4, Claude 중간 3·낮음 4)

규칙은 R2와 같다.
- 커밋하지 않는다. `docs/`를 고치지 않는다(이 파일 제외).
- 실제 LLM·메일·수집 호출을 하지 않는다.
- 계측 테스트는 emulator-5554에서만 한다.

원칙: 이중 과금과 중복 메일이 없어야 하고, 그날 실행이나 메일이 **알림 없이** 빠지면 안 된다.

## 높음
1. **실제 포그라운드 승격이 거절돼도 유료 실행이 시작된다.** (OpenAI 1)
   - WorkManager는 서비스 안에서 일어난 승격 거절을 로그로만 남긴다. 그래서 `setForeground()`가 정상 반환됐다고 승격이 된 것은 아니다.
   - Android 12(API 31) 이상에서 워커가 유료 실행에 들어가는 조건은 `PowerManager.isIgnoringBatteryOptimizations`가 참일 때로 한다.
   - 조건이 거짓이면 유료 호출 없이 끝낸다. 배터리 예외 필요 상태를 기록하고 알림을 띄운다. 시도 횟수에서 차감하지 않는다.
   - 앱 화면이 앞에 있거나 정확 알람이 막 울린 직후처럼 시스템이 허용하는 예외 구간은 서비스 경로가 처리하므로 워커에서 따로 다루지 않는다.
   - 테스트: 배터리 예외가 없을 때 유료 실행으로 들어가지 않는지 확인한다(판정 함수를 주입해 시험).
2. **다른 날짜의 미결 Batch 때문에 오늘 실행이 빠진다.** (OpenAI 2, Claude M1)
   - core: 복구 경로이거나 오늘이 아닌 날짜의 체크포인트에는 `deferBatch`를 적용하지 않는다. 기존처럼 pending으로 남겨 두고 오늘 실행을 계속한다.
   - 앱: `BatchDeferredException`을 받았는데 그 날짜의 `hasPendingBatch`가 거짓이면 미루지 않는다. 실패로 기록하고 알림을 띄운다.
   - 테스트: 어제 Batch가 진행 중일 때 오늘 실행이 끝까지 도는지(core), 앱이 엉뚱한 날짜로 미루지 않는지 확인한다.
3. **보고서를 게시한 직후 취소하면 그날 메일이 재시도 대상에 없다.** (OpenAI 3)
   - 일일 JSON을 게시할 때(또는 게시 직전) 그 보고서 메일을 "보낼 메일" 기록에 먼저 남긴다. 기존 예약 메일·재시도 기록 형식을 쓴다.
   - 그 뒤에 취소·마감이 오면 다음 실행의 메일 재시도가 이 메일을 보낸다.
   - 이미 보낸 기록과 중복으로 보내지 않는다. 기존 중복 방지 규칙을 유지한다.
   - 테스트: 게시 후·SMTP 전에 취소한 다음, 다음 실행에서 1회만 발송되는지 확인한다.

## 중간
4. **대기열 변경을 다음 실행보다 먼저 반영한다.** (OpenAI 5) 실행을 시작할 때 core 잠금을 잡은 직후, 설정을 읽기 전에 대기 중인 로컬 변경을 먼저 반영한다. 이 반영은 실행 잠금 안에서 직접 적용하는 경로를 쓴다. 실행 종료 뒤 반영도 유지한다.
5. **보류된 예약의 종료 경합을 메운다.** (OpenAI 4)
   - Claude는 `dispatch`가 `releaseReservation`을 다시 불러 메워진다고 봤다. 실제로 메워지는지 확인한다.
   - 메워지지 않으면, 서비스가 보류를 저장한 뒤 실행 플래그를 다시 확인한다. 비어 있으면 보류를 직접 이어서 처리한다.
   - 어느 쪽이든 경합 테스트를 넣는다.
6. **자정을 넘긴 예비 실행이 조건 대기에서 버려진다.** (OpenAI 6, Claude M2)
   - 예비 실행을 미뤘을 때의 유효성은 `backupRunDate`와 같은 규칙으로 판단한다. 설정 시각이 22:00 이상이면 날짜가 어제여도 허용한다.
   - 예비 미루기에는 본 실행과 다른 unique 이름을 쓴다.
   - 그래도 버려지는 경우에는 누락 알림을 띄운다.
7. **Batch 이어받기는 승격보다 상태 확인을 먼저 한다.** (Claude M3)
   - 이어받기는 먼저 Batch 상태만 짧게 확인한다. 승격하지 않고 10분 안에 끝낸다.
   - 아직 진행 중이면 다시 미룬다.
   - 결과가 준비돼 이어서 처리해야 할 때만 1번 조건으로 승격한다.
   - 1번 조건이 거짓이면 실패로 끝내지 않는다. 30분 뒤로 다시 미루고(6회 상한 안), 배터리 예외 필요 알림을 띄운다.
   - 상한까지 처리하지 못하면 "Batch 결과를 반영하지 못함" 알림을 띄우고 core 마감·격리 규칙을 따른다.
8. **사용자 취소는 그날 자동 재시도하지 않는다.** (OpenAI 7)
   - 사용자가 직접 누른 취소는 의도로 존중한다.
   - 상태를 "취소됨"으로 남기고, 누락 감지 경고에 포함한다. [지금 실행]은 그대로 할 수 있다.
   - 시스템 타임아웃·종료로 생긴 취소는 기존 규칙(시도 상한)을 따른다.
   - 두 경우를 구분해 기록한다.

## 낮음
9. 수동 실행에서 미룬 Batch는 이어받기 입력에 "수동 시작"을 담는다. 이 경우 예약 켜짐 여부와 `honorSchedule`를 무시하고 처리한다. (Claude L1)
10. 비용 없는 실패 뒤에 곧바로 `Result.retry()`하지 않는다. 백오프를 30분 이상으로 잡거나, 끝내고 다음 예비 실행에 맡긴다. 시도 2회가 30초 만에 소진되면 안 된다. (Claude L2)
11. 대기열 항목 하나가 반영에 실패해도 큐 전체가 막히면 안 된다. (Claude L3)
    - 항목별로 `Exception`을 잡아 실패 상태로 옮기고, 화면이 읽을 수 있게 상태를 노출한다.
    - `MainActivity.onStart`의 호출은 `runCatching`으로 감싸 앱이 강제 종료되지 않게 한다.
12. `RunLockedException`으로 끝난 시도는 시도 횟수 차감을 되돌린다. 또는 `beginAttempt`를 core 잠금을 잡은 뒤로 옮긴다. (Claude L4)
13. 테스트 보강 (Claude 16 부분)
    - 서비스 시작이 막혔을 때의 대체 경로
    - 1·2·3·6·7번의 계측 또는 단위 테스트
