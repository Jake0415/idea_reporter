# P10 수정 지시 — 3회차 (실제 재수집: github-issues 1건 — 과도하게 걸러짐)

규칙 동일(커밋·docs 수정·키 출력 금지, 실제 수집·LLM 실행 금지).
2회차 수정 후 실제 재수집 결과 github-issues **1건**(kelivo MCP 기능 요청). 어댑터 내부에서 어느 조건에 몇 건이 빠졌는지 기록이 없어 조정 근거가 없다. 목표는 하루 5~10건, 적합률 70% 이상.

1. **단계별 깔때기 기록** — 실행마다 `out/debug/github-issues-<날짜>.json`(원자 저장, 작성자 정보 없음)에 검색어·경로별로: 검색 `total_count`, 받은 건수, PR·봇 제외 후, 긍정 반응 하한 후, 점수 하한 후, 제외 라벨 후, 스타 하한 후(판정 보류 수 포함), 소유자 메모 제외 후, 다의어 검사 후, 최종(상한 전) 건수와 탈락 항목의 제목·URL(검색어별 최대 5개). 출처 결과 경고에는 합계 한 줄("받음 n → 최종 m, 가장 많이 뺀 단계: …").
2. **조건 완화(기본값)**:
   - 서버 반응 하한 `reactions:>=1`(긍정 반응 ≥ 1은 코드에서 유지).
   - 스타 하한 50 → **20**.
   - **검색어마다 두 경로 모두**(라벨 경로 + 제목 의도 경로) 실행하되, 검색 예산은 토큰 유무로: 토큰 있음 → 이슈 검색 최대 **24회**(검색 한도 30회/분, 헤더 기반 대기), 토큰 없음 → 9회(기존처럼 일부만, 순환 배정). 이슈 출처 시간 제한 60 → **90초**(토큰 없을 때 대기 포함). 일일 저장소 수집 우선순위는 유지.
   - 제목 의도어를 검색어마다 하나가 아니라 공통 집합 OR로 시도할 수 있는지 GitHub 문법 테스트로 확인하고, 가능하면 `in:title (support OR "add support" OR "feature request" OR "please add" OR "is there a way" OR integration)` 형태로(불가능하면 지금처럼 검색어별 하나).
3. 테스트: 깔때기 기록 내용(작성자 정보 없음), 토큰 유무별 예산, 두 경로 실행, 완화된 기본값 로드. 기존 테스트 기대값이 바뀌면 이유 보고.

## 완료 기준
- `:core:test --rerun-tasks` 통과. 1~3 한 줄씩 + 테스트 개수.
