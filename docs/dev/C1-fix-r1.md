# C1 수정 지시 1회차

근거: C1 1회차 리뷰(OpenAI 코드·Claude 코드·UX). 규칙은 [C1-candidates.md](C1-candidates.md)와 같다.
- 커밋하지 않는다. docs는 이 파일 말고는 고치지 않는다.
- 실제 호출을 하지 않는다.
- cron을 되살리지 않는다.
- emulator-5554에서만 테스트하고, 실제 폰에는 설치하지 않는다.
- JAVA_HOME을 직접 지정한다.

## 코드 — 높음
1. **요청 카드 비용이 매일 실행을 막음(Claude)**
   - 요청 카드 비용은 별도 원장 `out/cost-ledger-requested/<날짜>.json`에 기록한다.
   - "유료 실패·재시도" 판정용 `dailyCost()`(Workers `canRunNew`, `markFailure`, 첫 실행 재시도 판단)에서는 이 원장을 뺀다.
   - 일일·월간 예산 잔액 계산(`dailyBudgetExceeded`, 원장 합계, `MonthlyBudget`, 시험 실행 잔액)에는 더한다.
   - 백업(R4)의 원장 보호 규칙에 이 폴더를 넣는다. 가져오지 않고 보존한다.
   - 테스트: 07:00 전에 요청 카드 비용을 기록해도 그날 매일 실행이 막히지 않는지, 예산 잔액에는 반영되는지 확인한다.
2. **백업 재복원 시 요청 카드 삭제(공통)**
   - Backup의 deletes 계산에서 `requested/**` 경로를 뺀다. "없는 것만 채우기" 규칙을 지킨다.
   - 테스트: 같은 백업을 두 번 복원해도 기존 요청 카드가 남는지 확인한다.
3. **실제 청구가 상한을 넘을 수 있음(OpenAI)**
   - 요청 경로의 호출별 예약은 그 호출의 최대 출력 토큰(max_tokens), 실제 입력 토큰 수, 웹 검색 최대 횟수로 계산한 최대 비용으로 잡는다.
   - 최대 비용이 승인 상한이나 남은 일일 예산을 넘으면 실행하지 않는다.
   - 매일 실행 경로는 바꾸지 않는다.

## 코드 — 중간
4. **견적 직후 상한 재확인 실패**
   - 사용자가 승인하는 값은 "이번 요청에 쓸 최대 금액 = min(requestCardUsd, 남은 일일 예산)"으로 한다.
   - 실행 직전 재견적이 이 값을 넘을 때만 거절한다.
   - 거절하면 새 견적을 결과에 담아, 화면에서 재견적 확인 창을 다시 띄운다(분석의 requote와 같은 방식).
5. **유료 실패 후 새 요청을 못 함:** 선택이 바뀌면 `submitted`와 `outcome`을 초기화한다. 같은 선택으로 유료 호출을 자동으로 다시 하지는 않는다.
6. **병합 URL 검증(OpenAI):** 요청 경로에서도 `SAME_TOPIC` 기록으로 병합 멤버를 복원해 `CitationValidator`에 넘긴다. 원래 분류를 확인할 수 없는 병합 URL은 요청 인용에서 뺀다.
7. **후보 수와 select 건수 불일치(OpenAI)**
   - 후보는 선택 단계 통과 여부로 만들고, 기준 미달은 선택 단계의 탈락 기록(BELOW_PROFILE_THRESHOLD, SAME_TOPIC, OVER_QUOTA)으로만 만든다.
   - 중복 제거 단계의 탈락본이 대표를 지우지 않게 한다.
   - 테스트를 넣는다.
8. **추가 조사 URL의 민감 쿼리:** 공통 민감 쿼리 판별(`hasPrivateRssQuery` 계열)로 걸리는 URL은 근거에서 뺀다. 일반 인용과 보충 링크에 같은 검사를 적용한다.

## 코드 — 낮음
9. **복구 대기 판정:** 요청 실행도 분석처럼 `onLockAcquired = app::requireRunReady`를 넘긴다. 이 경우를 `BackupRecoveryBlocked`로 구분해 "복구 대기 중" 문구로 보여 준다.
10. **요청 메일의 앱 링크:** 매일 메일과 같은 `appLinks` 설정을 쓴다.
11. **계측 안정화(새 설치 시간 초과)**
    - 시작 전에 `recovery == READY && !operationRunning`을 기다린다. 알림 권한을 허용하고, `@After`에서 `operationRunning`을 초기화한다.
    - 테스트 날짜는 시스템 시간대 기준으로 정한다.
    - 길게 누른 뒤 "선택" 상태를 확인하고 나서 [카드 만들기]를 누른다.
    - 견적 실패 문구가 보이면 즉시 실패로 보고한다.
    - 새 설치 상태에서 C1 테스트만 단독으로 실행해도 통과해야 한다.

## UX
12. **훑어보기 좋게(높음)**
    - 행의 맨 위에 요약을 `bodyLarge`·Medium으로 둔다(2줄까지).
    - 그 아래에 누를 수 없는 작은 글씨(`labelMedium`, 흐린 색)로 "쓸 수 있는 기술 · 9.0점 · Hugging Face · 주제"를 쓴다. 48dp AssistChip은 쓰지 않는다.
    - 체크박스는 행 오른쪽 끝의 48dp 토글 영역으로 둔다. "후보 선택" 글자는 없애고, 접근성 설명을 "후보 선택: {요약}"으로 단다.
    - 출처 이름은 기존 출처 화면의 표시 이름을 쓴다(hf → Hugging Face).
13. **견적 창**
    - `request_card_quote` = "카드 만들기 전 확인"
    - `request_card_cost` = "예상 비용 약 $%1$.2f"
    - 새 문자열 `request_card_scope` = "선택 %1$d개 + 함께 쓸 근거 %2$d개 · 이번 요청 최대 $%3$.2f · 오늘 남은 예산 $%4$.2f"
    - `request_card_budget` = "예상 비용이 상한($%1$.2f)을 넘습니다. 설정 > 예산에서 바꿀 수 있습니다."
    - 추가 조사 스위치 아래 보조 문구(꺼져 있어도 보인다): "웹 검색 최대 3회·댓글 수집 포함, 비용이 늘어납니다"
14. **근거 부족 문구:** `request_card_insufficient` = "근거가 부족해 카드를 만들 수 없습니다. 위의 '추가 조사'를 켜면 관련 글을 더 찾아봅니다(비용이 늘어납니다)."
15. **배지:** "요청" 배지를 "내가 고른 카드"로 바꾼다. 태그 알약과 구분되는 테두리 알약(`tertiary` 글자색)으로 둔다. "카드에 쓰임"도 같은 알약 스타일로 두고, 반대 표시는 "카드에 안 쓰임"으로 쓴다.
16. **선택 안내와 제한**
    - 머리 아래 한 줄: `candidates_select_hint` = "오른쪽 칸을 체크해 1~3개를 고르면 상세 카드를 만들 수 있습니다(유료)."
    - 3개를 고르면 나머지 체크를 끄고, 하단 바에 "최대 3개"를 표시한다.
17. **하단 바:** Row로 만들고 세로 가운데 정렬한다. 구성은 "n개 선택"·[선택 해제]·[카드 만들기]다. 좁은 화면에서는 [카드 만들기]를 가로로 채운다.
18. **제목과 단위**
    - `candidates_title` = "카드 후보"(날짜 머리가 따로 있다)
    - `candidates_score` = "%1$.1f점"
    - 펼친 상태의 기준 미달 토글: "기준 미달 %1$d건 접기"
    - 빈 상태 아래에 [보관함으로] 링크를 둔다.
19. **SC-01 진입 링크:** "카드 후보 n"은 링크 색(`tertiary`)으로 보이게 하고, 터치 영역은 48dp로 둔다.
20. **메일 후보 구역**
    - 항목은 두 줄로 쓴다: 굵게 쓴 요약 + 작은 회색 줄 "쓸 수 있는 기술 · 9.0점 · 원문 열기".
    - 카드가 0개이면 목차 제목을 숨긴다.
    - 바닥글 금액은 `.2f`로 쓴다.
