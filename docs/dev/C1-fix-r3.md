# C1 수정 지시 3회차

근거: C1 3회차 리뷰(OpenAI 높음 1·중간 2, Claude 높음·중간 없음·낮음 2, UX 중간 2·낮음 3). 규칙은 [C1-fix-r2.md](C1-fix-r2.md)와 같다.

## 결정(Claude): 웹 검색은 공급자 쪽 입력 한도를 걸 수 없다
그래서 검색 결과가 길면 실제 정산액이 예약을 넘을 수 있다. 엄격한 보장 대신 넘는 폭을 작게 묶고 사용자에게 알린다.

1. **추가 조사 검색 모델 고정:** 추가 조사의 웹 검색은 분류 단계 모델과 상관없이 같은 공급자의 가장 싼 모델(입력 단가 최저, 모델 카탈로그 기준)로 돌린다. 이 경우 Opus를 골랐을 때 생기는 큰 초과를 없앤다.
2. **예약:** 회당 50,000토큰(그 모델 단가) + 검색 수수료로 예약한다. 견적 표시도 같은 값을 쓴다.
3. **한 번 넘기면 다음 요청 차단:** 정산액이 승인액을 넘었으면 `cost-ledger-requested/<월>.blocked` 표식을 남긴다(분석과 같은 방식). 그날 이후 요청 카드 견적은 "지난 요청이 예상보다 많이 나와 이번 달 요청 카드를 멈췄습니다 · 설정 > 예산에서 다시 허용"으로 막는다. 설정에서 해제할 수 있게 한다. Backup.kt의 `-requested` 패턴은 그대로 쓴다.
4. **견적 창 안내:** 추가 조사를 켜면 보조 문구를 보여 준다. "웹 검색 결과 길이에 따라 실제 비용이 조금 늘 수 있습니다(최대 약 $%1$.2f)". 최대값은 회당 100,000토큰 기준으로 계산한다.
5. 테스트: 검색 모델이 가장 싼 모델로 고정되는지, 초과 정산이면 차단 표식이 생기고 다음 견적이 막히는지, 해제하면 다시 되는지 확인한다.

## 코드
6. **댓글 견적 불일치:** 새 댓글과 저장된 댓글에 같은 개수·길이 제한(`commentsPerItem`, 500자)을 적용한다. 견적과 실행이 제한을 적용한 같은 입력을 같은 방식으로 직렬화한다.
7. **월 사용액 표시:** `MonthlyBudget.warnings()`와 `status()`의 월 전체 사용액에 요청 원장의 월 합계를 더한다. 잔액·사용률·경고가 같은 합계를 쓴다. 테스트를 넣는다.

## UX
8. **하루 최대 초과 창:** scope의 3번째 값은 설정값 `requestCardUsd`를 쓴다. 남은 금액은 4번째 값이 보여 준다. 하루 최대 경고의 금액은 실제 설정값 `requestDailyUsd`로 쓴다. 지금은 $1.00 고정 문구로 보인다.
9. **SC-11 보조 문구**
   - `budget_daily_card_help` = "매일 자동 실행에 쓰는 금액"
   - `request_card_daily_limit_help` = "내가 고른 카드에 쓰는 금액, 매일 예산과 따로 계산"
10. **scope 두 줄:** `request_card_scope` = "선택 %1$d개 + 함께 쓸 근거 %2$d개\n이번 요청 최대 $%3$.2f · 오늘 요청 예산 남음 $%4$.2f"
11. **추가 조사 스위치:** 하루 최대·월 예산·차단 표식 때문에 막힌 경우에는 스위치를 끈다(비활성).
12. **캡처:** 3개를 고른 하단 바 캡처를 추가한다.
