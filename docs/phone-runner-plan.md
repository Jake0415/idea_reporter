# 폰에서 직접 실행하는 방식으로 전환 — 구현 플랜과 문제점

작성 2026-11-24. 사용자 요청: "매일 아침 핸드폰에 스케줄러를 등록하고 폰 안에서 동작. 사용자가 필요하면 직접 수정. 아침 7시 예약 실행 지원."

## 1. 무엇이 바뀌나

| | 지금(11-23 결정) | 바꾼 뒤 |
|---|---|---|
| 매일 실행 | GitHub Actions 07:00 | **폰 예약 실행 07:00**(시각 수정 가능) + 앱의 [지금 실행] |
| 수집·LLM·메일 | Actions 러너 | **폰** (core를 앱 안에서 실행) |
| 기록 보관 | 공개 저장소 `data` 브랜치 | **폰 내부 저장소**(앱 전용 폴더) |
| 키 보관 | GitHub Secrets | **폰 Keystore**(Anthropic·OpenAI·GitHub 토큰·Gmail 앱 비밀번호) |
| 앱 역할 | 보기·조작(inbox로 요청) | **실행·보기·설정 모두**(직접 반영, inbox 불필요) |

이 방식은 원래 설계(`menu.md` SC-00·SC-11, `design.md` §6 `app/work`·`app/mail`)로 돌아가는 것이다. 메뉴 명세 상당 부분을 그대로 쓸 수 있다.

## 2. 구조

```
[AlarmManager 07:00 정각 알람] ─┐
[WorkManager 하루 1회(예비)]   ─┼─▶ CollectorRunService (포그라운드 서비스, 알림 "수집 중")
[앱의 지금 실행 ↻]             ─┘        │
                                         ▼
                         core CollectorRuntime(outDir = 앱 filesDir/out, configDir, secrets=Keystore)
                         ① 수집 → ② 분류 → … → ⑨ 저장·메일  (PC --scheduled와 같은 순서, 일요일 트렌드)
                                         ▼
                         Room(화면용 캐시) 갱신 → 완료 알림 "오늘 카드 n개"
```

- **core 재사용 방식:** PC와 같은 파일 저장소(`out/` JSON)를 앱 전용 폴더에 둔다. 동작이 PC와 똑같아지고 P13(Batch)·P11(메일)의 안전장치를 그대로 쓸 수 있다. 화면은 실행이 끝날 때 그 결과를 Room에 반영해 읽는다(P15 Room·FTS 재사용).
- **설정 직접 수정:** 사용자가 앱에서 고친 값은 앱 폴더의 `config/*.local.json`·`config/prompts/`에 바로 쓴다. core가 이미 이 파일을 읽는다. inbox를 거치지 않는다.
  - 수정 대상: 실행 시각, Wi-Fi만, 충전 중만, 키, 모델, 예산, 출처, 프롬프트, 내 기준

## 3. 07:00 예약 실행 — 방법과 한계
1. **정각 알람:** `AlarmManager.setExactAndAllowWhileIdle`로 07:00(사용자 설정 시각)을 예약한다. 절전(Doze) 중에도 깨운다.
   - Android 14부터 정확한 알람에는 **"알람 및 리마인더" 권한(`SCHEDULE_EXACT_ALARM`)을 사용자가 직접 켜야** 한다. 앱이 설정 화면으로 안내한다.
   - 권한이 없으면 부정확 알람(수 분~수십 분 늦을 수 있음)으로 대신한다.
2. **실행:** 알람 수신 → 포그라운드 서비스(`dataSync` 타입, 알림 표시)로 파이프라인을 돌린다. 정확한 알람에서 시작한 포그라운드 서비스는 백그라운드 시작 제한의 예외다.
3. **예비 경로:** WorkManager 하루 1회 작업이 "오늘 실행 기록 없음"을 확인하면 대신 실행한다. 알람을 놓쳤을 때, 폰이 꺼져 있었을 때를 위한 것이다(PC의 StartWhenAvailable과 같은 역할).
4. **재부팅·앱 업데이트·시각 변경:** `BOOT_COMPLETED`·`MY_PACKAGE_REPLACED`·`TIME_SET`·`TIMEZONE_CHANGED`를 받으면 알람을 다시 등록한다.
5. **겹침 방지:** 예약 실행과 [지금 실행]은 core 실행 잠금과 서비스 단일 실행으로 겹치지 않게 한다.
6. **조건:** Wi-Fi만·충전 중만 옵션이 있다. 조건이 맞지 않으면 기다렸다가 조건이 맞을 때 실행한다. 단 오늘 안에만 실행하고, 날짜가 넘어가면 건너뛰고 기록을 남긴다.

## 4. 문제점과 대응

| # | 문제 | 영향 | 대응 |
|---|---|---|---|
| 1 | **삼성 배터리 관리**(사용하지 않는 앱 절전, 백그라운드 제한)가 알람·서비스를 막을 수 있다 | 07:00 실행이 빠지거나 늦어진다 | 첫 실행 마법사에서 ① 배터리 최적화 예외 요청 ② 삼성 "절전 예외 앱" 설정 화면으로 안내 ③ 마지막 실행 시각을 오늘 화면에 표시하고, 빠졌으면 경고 띠를 띄운다. **완전한 보장은 불가능**하다(안드로이드 정책) |
| 2 | 정확한 알람 권한을 사용자가 켜야 한다(Android 14+) | 안 켜면 부정확 알람 | 권한 안내 화면을 둔다. 꺼져 있으면 설정에 "정각 실행 꺼짐" 표시 |
| 3 | **Batch API 대기(최대 90분)**는 폰에서 포그라운드 서비스를 오래 유지해야 한다. 배터리·발열이 생기고 Android 15에서는 `dataSync` 하루 6시간 제한이 있다 | 배터리 소모, 강제 종료 위험 | **폰 기본값은 Batch 끔(즉시 호출)**. 비용은 분류 단계만 약 2배로, 하루 몇 센트 차이다. 켜면 "제출 → 서비스 종료 → 30분 뒤 WorkManager로 결과 회수"의 2단계로 한다(P13 재개 기능 사용) |
| 4 | **키 4종이 폰에 저장**된다(Anthropic·OpenAI·GitHub·Gmail 앱 비밀번호) | 폰 분실 시 위험 | Keystore AES-256-GCM(P15 재사용), 백업 제외, 화면 캡처 방지. 분실하면 각 서비스에서 키를 폐기한다(설정 안내에 명시) |
| 5 | P15에서 앱 APK에서 뺀 **Anthropic·OpenAI SDK, Angus Mail을 다시 넣어야** 한다 | 안드로이드 호환성 확인 필요, APK 크기 증가(대략 +10~20MB) | 안드로이드에서 실제 호출 경로를 계측 테스트로 검증한다(MockWebServer, 가짜 SMTP). R8 keep 규칙을 정리한다. Angus Mail이 안드로이드에서 문제가 있으면 대체한다. 인증서 검증을 끄는 방법은 금지 |
| 6 | core가 **작업 위치 기준 상대 경로**(`out/`, `config/`, `.env`)를 쓴다(`Main.kt`, `GitHubIssuesAdapter`의 `out/cache`, `PipelineConfig.LOCAL_PATH`, `FilePromptStore` 기본값) | 안드로이드에서 그대로는 동작하지 않는다 | **core 리팩터링:** `Main.kt`의 일일 실행 조립부를 `collector.runtime.CollectorRuntime(outDir, configDir, secrets, clock)`으로 옮긴다. PC `Main`과 앱이 함께 쓴다. 모든 경로를 주입받게 한다 |
| 7 | **GitHub Actions와 이중 실행** | 비용 2배, 메일 2통 | **Actions의 매일 예약(cron)을 끈다.** 수동 실행만 남기거나 workflow를 삭제한다(결정 필요) |
| 8 | **기록이 폰에만** 있다 | 폰 분실·초기화 시 카드·추적·비용 기록이 사라진다 | (선택) 백업: 설정에서 JSON 내보내기/가져오기(SC-11 백업, 키 제외). 또는 P14 data 브랜치에 자동 백업 push(결정 필요) |
| 9 | 실행 시간(수집+분류+작성+메일 약 3~10분) 동안 **모바일 데이터·배터리**를 쓴다 | 데이터 수 MB, 배터리 소량 | Wi-Fi만·충전 중만 옵션. 기본값은 둘 다 끔 |
| 10 | P16에서 만든 **보기·조작 흐름**(inbox 요청 칩, Actions dispatch, 저장소 연결 마법사)이 대부분 필요 없어진다 | 이미 한 작업 일부 폐기 | 화면 틀(카드·상세·추적·보관함·설정·프롬프트 편집)은 그대로 쓴다. 데이터 출처만 "동기화 결과" → "폰 실행 결과"로 바꾼다. inbox·dispatch 코드는 지운다 |
| 11 | 같은 날 다시 실행·메일 하루 1회·미결 Batch 처리 | 중복 메일·비용 | core 규칙을 그대로 쓴다(P11·P13). 폰도 PC와 같은 파일 저장소를 쓰기 때문이다 |
| 12 | 사용자가 시각을 바꾸면 | 알람 재등록 필요 | 설정 저장 즉시 알람을 다시 등록하고 다음 실행 시각을 표시한다. 오늘 시각이 이미 지났으면 내일부터 실행한다(옵션으로 "지금 한 번 실행") |

## 5. 구현 단계 (기존 방식: Codex 개발·OpenAI·Claude·UX 동시 리뷰·5회 이내)
- **P16 정리:** 진행 중인 P16 수정 1회차는 화면 틀만 살린다. 리뷰를 거쳐 커밋하고, inbox·dispatch 흐름은 R2에서 걷어낸다.
- **R1 core 실행 런타임 분리:** `CollectorRuntime`과 경로 주입을 만든다. PC `Main`·Actions도 이것을 쓰게 바꾼다. 테스트를 유지한다(core 364개).
- **R2 앱에서 실행:**
  - 제외했던 SDK를 복원하고 안드로이드에서 호출되는지 검증한다.
  - `CollectorRunService`(포그라운드)를 만든다.
  - 정각 알람, 예비 WorkManager, 재부팅·시각 변경 재등록, 실행 잠금을 넣는다.
  - 실행이 끝나면 Room에 반영하고 알림을 띄운다.
  - Batch 기본값은 끈다.
- **R3 설정 화면(원래 명세로 복원):**
  - SC-00 첫 실행: AI 키 → 메일·테스트 발송 → 내 기준 → 권한(알림·정확한 알람·배터리 예외) → 첫 실행
  - SC-11: 일정(시각·Wi-Fi·충전), 키, 모델, 예산
  - SC-07: 출처
  - SC-09: 내 기준
  - SC-15/16: 프롬프트 편집. 직접 저장하고, 시험 실행도 가능해진다
- **R4 정리:** Actions 예약 끄기, 백업(선택), 문서 갱신(`CLAUDE.md`·`design.md`·`menu.md`·`scripts`), 실제 폰 설치·하루 동안 예약 실행 확인.

## 6. 사용자 결정 (2026-11-24)
1. **GitHub Actions:** 매일 예약(cron)만 끄고 수동 실행(`workflow_dispatch`)은 남긴다. 폰이 고장 났을 때 임시로 쓸 수 있게 하기 위해서다.
2. **기록 백업:** 수동 내보내기·가져오기를 둔다(설정 > 백업, JSON, 키 제외). 자동 백업은 하지 않는다.
3. **폰 Batch:** 기본은 끈다(즉시 호출). 설정에서 켤 수 있고, 켜면 2단계 회수 방식으로 동작한다.
4. **사업성 분석:** 폰에서 직접 실행한다. 실행 전 추정 비용 확인과 금액 상한은 유지한다.

## 7. (원래) 결정이 필요했던 것
1. **GitHub Actions:** 매일 예약만 끄고 수동 실행은 남길까, workflow를 삭제할까? 또는 폰이 실패한 날만 Actions가 대신 실행하는 예비로 둘까? 예비 방식은 이중 실행을 막는 확인이 필요해 복잡하다.
2. **기록 백업:** 없음 / 수동 JSON 내보내기 / data 브랜치 자동 백업(공개 저장소라 공개됨) 중 하나.
3. **폰 Batch:** 기본 끔(즉시 호출, 분류 비용 약 2배·하루 몇 센트)으로 해도 되는지.
4. **사업성 분석(OpenAI, 요청형):** 폰에서 직접 실행해도 되는지. 실행 전 추정 비용을 확인하는 단계는 유지한다.
