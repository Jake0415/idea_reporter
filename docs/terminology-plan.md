# 용어 쉽게 바꾸기 — 수정 플랜

작성 2026-11-23. 사용자 지적: "신호"처럼 어려운 용어가 있다.

## 원칙
- **화면·메일·콘솔 출력·프롬프트 제목처럼 사용자가 읽는 말만 바꾼다.** 코드 식별자(`tech-signal`, `techSignals`, `SignalRef`, JSON 필드)와 저장 파일 형식은 그대로 둔다. 바꾸면 저장된 기록·프롬프트 수정본·테스트가 깨진다.
- 한 개념에는 한 단어만 쓴다(메일·앱·문서가 같은 말).
- "무엇을 보여 주는지"가 바로 읽히는 말을 고른다. 업계 용어(신호·프로필·임계값·깔때기)는 피한다.

## 1. 바꿀 용어 (표시 문구)

### A. "신호" 계열 — 가장 많이 나옴

| 지금 | 바꿀 말 | 뜻 | 나오는 곳 |
|---|---|---|---|
| 기술 신호 | **쓸 수 있는 기술** | 서비스를 만들 재료(모델·라이브러리·API) | 카드 근거 칸, 프로필 이름, 검증 메시지, 목업 |
| 수요 신호 | **사람들의 요청·불편** | "이런 게 있으면 좋겠다"는 글·이슈 | 카드 근거 칸, 트렌드 표 열 "수요", 목업 |
| 시장 신호 / 경쟁 신호 | **이미 나온 제품** | 같은 일을 하는 출시 제품 | 트렌드 과열 줄, 프로필 이름, 목업 |
| 신호 프로필 (SC-08) | **분류 기준** | 기술·요청·제품을 나누는 기준과 점수표 | 설정 화면, 프롬프트 목록 |
| 신호 강도 | **관련 글 수(최근 7일)** | 추적 아이디어와 관련된 최근 글 수 | 추적 업데이트(메일 숫자 옆), SC-03·04 |
| 관련 신호 | **관련 글** | 추적 중 새로 잡힌 글 | 트렌드 목업 |
| 관심 신호 | **관심 표시** | ★ 같은 사용자 반응 | 트렌드 목업 |
| 유행 과열 신호 | **제품이 몰린 테마** | 출시 제품만 많고 요청은 적음 | 트렌드 목업 |

※ "수신 신호"는 현재 문구에서 찾지 못했습니다. "수요 신호"를 말씀하신 것으로 보고 위 표에 넣었습니다.

### B. 처리 과정 용어

| 지금 | 바꿀 말 | 나오는 곳 |
|---|---|---|
| 깔때기 | **단계별 건수** | 일일 메일 머리, SC-01·SC-10 |
| 점수 통일 | **점수 맞추기** | 단계별 건수 |
| 보강 | **댓글·과거 기록 붙이기** | 단계별 건수 |
| 후보 | **카드 후보** | 메일 제목·단계별 건수 |
| 프로필 · 임계값 통과 | **분류 · 기준 점수 통과** | 콘솔 출력(Main), SC-08 |
| 인용 | **근거 링크** | 검증·탈락 사유 |
| 블록-프로필 불일치 | **근거 칸과 분류가 맞지 않음** | 탈락 사유 |
| 분류 상한 초과 | **같은 분야 카드 수 초과** | 탈락 사유 |
| 수신 n명 | **받는 사람 n명** | 메일 발송 완료 줄 |

### C. 트렌드 리포트 용어

| 지금 | 바꿀 말 |
|---|---|
| 과열 / (과열) | **제품 몰림** / (제품 몰림) |
| 과열 경고 · X 시장 신호 n건 | **제품 몰림 · X 출시 제품 n건** |
| (의심) | **(스타 조작 의심)** |
| 재등장 미매핑 n건 | **테마에 못 넣은 반복 글 n건** |
| 희소 태그 n개 제외 | **너무 드문 태그 n개 제외** |
| 너무 넓어 제외한 태그 | (그대로 — 이미 쉬움) |
| 포크/스타 | **포크 비율** |
| 분석 후보 ◆ | (그대로 — 리포트 머리에 "◆ = 사업성 분석을 요청할 만한 테마" 한 줄 설명 추가) |

## 2. 고칠 파일

1. **메일·리포트 출력:** `report/HtmlRenderer.kt`, `trend/TrendReportRenderer.kt`, `trend/TrendAnalyzer.kt`(경고 문구), 분석 리포트 렌더러.
2. **검증·탈락 사유:** `stage/IdeaGenerator.kt`, `analysis/OpportunityJudge.kt`, `pipeline/FullPipeline.kt`.
3. **콘솔 출력:** `dev/Main.kt`, `mail/MailDelivery.kt`, `prompt/PromptCatalog.kt`(프롬프트 표시 이름).
4. **프로필 표시 이름:** `profiles/*/profile.json`의 `name`, `match.md`·`analysis.md` 제목 줄.
5. **프롬프트 본문(`ideas.md`, `classify.md`, `track.md`):** LLM이 읽는 말이라 결과에는 영향이 없다. 다만 사용자가 직접 고치는 화면에 나오므로 같은 말로 맞춘다. 블록 이름(`techSignals` 등)은 출력 형식이라 그대로 두고, 뜻을 설명하는 문장만 바꾼다. **기본 프롬프트가 바뀌는 것이라 카드 품질을 한 번 확인한다**(시험 실행 1회, 약 $0.1).
6. **목업:** `mockup/index.html`, `mockup/trend.html`.
7. **문서:** `docs/menu.md`(SC-08 이름 "분류 기준"), `docs/design.md`, `docs/business-scout-plan.md`, `CLAUDE.md`. 문서 맨 앞에 "용어집" 표를 하나 두고(코드 이름 ↔ 화면 이름), 나머지는 화면 이름으로 쓴다.
8. **테스트:** 문구를 확인하는 테스트의 기대값을 함께 고친다.

## 3. 진행 순서 (기존 방식: Codex 개발 · 동시 리뷰 · 5회 이내)
1. 용어 확정 — 이 표를 사용자가 확인·수정
2. 코드 표시 문구 + 테스트 (1~4, 8) — 식별자 변경 없음을 리뷰에서 확인
3. 프롬프트 본문 정리 (5) + 시험 실행 1회 (비용 확인 후)
4. 목업·문서 (6, 7)
5. 커밋 1건: `♻️ refactor: 표시 용어 쉽게 — 신호→기술/요청/제품, 깔때기→단계별 건수 …`
