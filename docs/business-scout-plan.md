# 기술 트렌드 리포트 + 요청형 사업성 분석 플랜 (초안 v3)

> 상태: **기획 초안 — v3 결정 반영, 남은 결정 대기**(§9). 확정되면 design.md·menu.md에 F-xx·SC-xx로 옮긴다.
> 한 줄 요약: **기술 분석은 자동, 사업성 분석은 요청할 때만.** 매주 기술·오픈소스 트렌드 리포트를 코드로 만들어 보낸다(LLM 0원). 사업성 분석은 내가 리포트를 보고 **요청할 때만** OpenAI `gpt-6.2-sol`(추론 high)이 리포트 자료를 바탕으로 분석해 알려 준다. 토큰 비용이 큰 단계를 필요할 때만 쓰는 구조다.

> 화면 시안: [mockup/trend.html](../mockup/trend.html) (`node mockup/serve.mjs` → http://localhost:5179/trend.html) — UX 구성안·전달 흐름 + 화면 SC-17~28·알림·메일 2종, 샘플 데이터.

## 버전 기록
- **v3:** 사업성 분석을 자동 주간 실행에서 **요청형**으로 바꿨다. 자동으로 도는 것은 코드만 쓰는 기술 리포트뿐이다(§3). 요청 방식·범위·비용 확인은 §5.
- v2: 보고 항상 발송, 사업성 낮은 분야는 점수 순 목록 + 간단 보기, OpenAI `gpt-6.2-sol` 추론 high. → 목록·간단 보기·모델은 v3에서도 유지하고, **요청한 분석의 결과**에 적용한다.
- v1: 주 1회 자동 발굴 → 의뢰서. (폐기: 매주 토큰 비용 과다)

## 1. 구조 한눈에

| | ① 기술 트렌드 리포트 | ② 사업성 분석 |
|---|---|---|
| 언제 | **자동**, 주 1회(기본 일요일) | **내가 요청할 때만** |
| 무엇으로 | 코드(집계·통계) | OpenAI `gpt-6.2-sol`, 추론 high |
| 비용 | **0원** | 요청 1건마다 발생(실행 전 추정 비용 표시·확인) |
| 입력 | 쌓인 수집·분류 데이터 | ①의 리포트 자료 + 근거 항목 + 내 기준 + 피드백 |
| 결과 | 기술·오픈소스 트렌드 표, "분석해 볼 만한 테마" 표시 | 분야별 사업성 점수 순 목록, 기준 통과 시 개발 의뢰서, 간단 보기용 기록 |

매일 아이디어 카드(현재 파이프라인)는 그대로 돈다. 카드·★·관심 없음 기록은 ①의 지표와 ②의 입력으로 쓴다.

## 2. 쓸 수 있는 데이터 (현재 저장분 기준)

| 데이터 | 위치 | 트렌드에 쓰는 법 | 한계 |
|---|---|---|---|
| 분류된 신호(프로필·주제 키·주제명·태그·점수·요약) | `out/<날짜>.json` `classified` | 주제별 언급 수·출처 다양성·수요/시장 비율 | 주제 키가 날마다 LLM이 붙인 것이라 **같은 주제가 다른 키**로 나뉨 → §4-2 |
| 원 항목(출처·rawScore·게시 시각·태그, GitHub `language`·`forks`·`license`) | 같은 파일 `items`, `dropped` | 오픈소스 언어·라이선스·주제(topics) 분포 | **이미 본 항목은 분류되지 않음**(ALREADY_SEEN) → 재등장 횟수는 따로 세야 함 |
| 점수 스냅샷 | `out/metrics.json` (`MetricSnapshot`, 30일) | GitHub 스타·HN 점수 **증가 속도** | 수집에 걸린 날만 찍힘(띄엄띄엄) |
| 주제 이력 | `TopicHistory` | 연속 등장·재등장 | 위와 같은 키 문제 |
| 카드·피드백·추적 | `out/<날짜>.json` `cards`, 피드백, `tracked.json` | 내 취향, 거절 이유, 추적 신호 강도 | — |
| 탈락 기록 | `dropped` | 스팸 복제 저장소 급증(예: 11월 20일 96건) = **과열 신호** | — |

**가장 큰 문제: 쌓인 기간이 2일뿐이다.** 트렌드는 최소 2주가 있어야 의미가 있다. §4-1의 **과거 데이터 채우기**(HN·GitHub는 API로 과거 4주를 가져올 수 있음)로 보완하고, 데이터가 모자란 주에는 "데이터 부족·잠정"을 표시한다.

## 3. 흐름

```
[매일 파이프라인] ──쌓임──▶ out/*.json, metrics.json, 피드백

━━ ① 자동: 기술 트렌드 리포트 (주 1회, LLM 0원) ━━━━━━━━━━━━━━━━━━━━━
  a. 일별 집계·재등장·스냅샷 보강 (코드)
  b. 주제 묶기 (코드 규칙 + 저장된 별칭표)
  c. 트렌드 계산 (코드): 기술 트렌드 · 오픈소스 트렌드 · 과열 경고
  d. "분석해 볼 만한 테마" 표시 (코드 규칙)
  e. 리포트 발송·저장 → out/trend/<주>.json (②의 입력 자료)

━━ ② 요청형: 사업성 분석 (내가 요청할 때만) ━━━━━━━━━━━━━━━━━━━━━━━
  요청: 테마 지정 / 이번 주 전체 / 추가 질문
    → 추정 비용 표시 → 내가 확인
    → 기회 분야 정리 → 코드 관문 → 평가표(sol high) → (선택) 반대 검토
    → 결정: 기준 통과 분야 있으면 개발 의뢰서 / 없으면 "사업성 미달"과 이유
    → 결과: 점수 순 목록 + 의뢰서(있을 때) + 분야별 심사 기록 저장
  간단 보기: 저장된 심사 기록 표시 (0원)
```

원칙은 C안과 같다: **숫자는 코드가 계산하고, LLM은 해석·판단만 한다.** LLM에 주는 수치는 코드가 만든 리포트 표이고, 분석 결과의 수치·근거는 코드가 원본과 대조한다.

## 4. ① 기술 트렌드 리포트 (자동, 코드만)

### 4-1. 데이터 채우기·보강
- **과거 채우기(처음 1회, 선택):** HN Algolia(`created_at_i` 범위)·GitHub 검색(`created:` 기간 범위)으로 지난 4주를 수집해 `out/backfill/`에 저장. 리포트 자체는 코드로 만들지만, 과거 항목에 프로필·주제가 없으므로 **분류는 기존 분류 단계(싼 모델)로 1회** 돌린다(수백 건, 실행 전 추정치 표시). 분류 없이 태그·검색어 기준 집계만 쓸 수도 있다(0원, 정확도 낮음) — §9 결정.
- **매일 보강:** 이미 본 항목도 **재등장 횟수와 점수 스냅샷은 기록**한다(지금은 탈락으로만 남음). 파이프라인 끝에 일별 집계 `out/trend/daily-<날짜>.json`(주제·태그·언어·라이선스별 개수)을 만든다.

### 4-2. 주제 묶기 (코드)
- LLM 없이 묶는다: 주제 키 정규화(이미 있는 규칙), 주제명·태그의 단어 겹침, GitHub topics·HF 태그 일치로 **테마**를 만든다.
- 묶은 결과는 `별칭 → 테마` 표(`out/trend/themes.json`)로 저장해 주마다 이어 쓴다. 잘못 묶이면 내가 표를 고친다(나중에 앱 화면).
- 코드 묶기가 부족하면 LLM 묶기(sol low, 새 별칭만)를 **선택 기능**으로 켤 수 있게 둔다(기본 꺼짐).

### 4-3. 트렌드 계산
테마마다 계산한다.

| 지표 | 계산 | 의미 |
|---|---|---|
| 언급 수 추이 | 주별 항목 수(최근 4주) | 관심의 양 |
| 증가율 | 이번 주 ÷ 지난 3주 평균 | 뜨는 중인가 |
| 출처 다양성 | 언급된 출처 종류 수 | 한 동네 유행인가 |
| 수요 비율 | demand-signal 수·비율, 대표 불편 글 | 사람이 원하는가 |
| 시장 비율 | market-signal 수(출시 제품) | 이미 붐비는가 |
| OSS 속도 | 테마 저장소 하루 스타 증가 중앙값, 포크/스타 비율 | 만드는 사람이 몰리는가, 실제로 쓰는가 |
| OSS 성숙도 | 허용 라이선스(MIT·Apache) 비율, 주요 언어 | 재료로 쓸 수 있는가 |
| 과열 경고 | 복제·스팸 저장소 급증, 시장 신호 급증 | 이미 늦었나 |
| 내 반응 | 관련 카드 ★·관심 없음 수 | 내 취향 |

### 4-4. "분석해 볼 만한 테마" 표시 (코드 규칙)
사업성 분석을 요청할지 고르기 쉽게, 아래 조건을 채운 테마에 표시(◆)를 붙인다. 판단이 아니라 **요청 후보 안내**다.
- 증가율 ≥ 1.5 **그리고** 수요 신호 ≥ 1 **그리고** 출처 2종 이상
- 과열 경고가 있으면 표시 대신 "과열" 표시
- 규칙의 숫자는 설정으로 바꿀 수 있다.

### 4-5. 리포트 구성 (매주 자동 발송)

```
제목: [기술 트렌드] 11월 4주 — 뜨는 테마 3 · 분석 후보 ◆2

1. 이번 주 요약 (코드가 만든 3줄: 가장 뜬 테마, 가장 빠른 저장소, 과열 경고)
2. 기술 트렌드 표 — 뜨는 테마 10 · 지는 테마 5
   ◆ 로컬 소형 모델 문서 검토  · 12건(+180%) · 출처 3 · 수요 2 · 시장 1 · [사업성 분석 요청]
     MCP 서버 도구             · 20건(+40%)  · 출처 2 · 수요 0 · 시장 4
3. 오픈소스 트렌드 표 — 빠르게 크는 저장소 10 · 언어·라이선스 분포 · 과열(복제 급증) 목록
4. 지난 분석 요청 결과 요약 (있을 때)
5. 데이터 상태 (기간, 잠정 표시, 수집 실패 출처)
```
- 요약 3줄도 코드 템플릿으로 만든다(LLM 0원).
- 리포트 자료(`out/trend/<주>.json`)에는 테마별 지표와 **대표 근거 항목 ID·URL**을 함께 저장해, ② 분석 때 그대로 입력으로 쓴다.

## 5. ② 사업성 분석 (요청형)

### 5-1. 요청 방법
| 요청 종류 | 내용 | 비용 크기 |
|---|---|---|
| **테마 지정 분석** | 리포트에서 고른 테마 1~3개만 분석 | 작음(기본 권장) |
| **이번 주 전체 분석** | 리포트 전체에서 기회 분야 3~5개를 찾아 분석 | 큼 |
| **추가 질문** | 이미 한 분석 결과(심사 기록)를 맥락으로 질문 | 작음 |

- 경로: PC `Main --analyze <테마 ID…>` / `--analyze all` / `--ask <분석 ID> "<질문>"`. 앱에서는 리포트의 [사업성 분석 요청] 버튼(메일 링크 → 앱 화면). 메일 자체에서 바로 실행하지는 않는다.
- **실행 전 확인:** 입력 크기로 추정 비용을 계산해 보여 주고, 내가 확인해야 실행한다. 요청 1건 상한(`analysisBudgetUsd`)과 월 상한을 넘으면 실행하지 않는다.
- 같은 테마·같은 주 자료로 이미 분석했으면 저장된 결과를 먼저 보여 준다(다시 돌릴지 선택).

### 5-2. 분석 단계 (요청 1건 안에서)
1. **기회 분야 정리**(sol high): 요청한 테마(또는 전체 리포트)의 지표·근거 + 최근 카드 + 피드백 + 내 기준으로 "뜨는 기술 × 불편 × 빈 시장" 분야를 정리한다(테마 지정이면 테마당 1~2개). 근거는 **입력에 있는 항목 ID·URL만** 쓰고 코드가 검증한다.
2. **코드 관문**(0원) — 걸린 분야는 의뢰 후보에서 빠지지만 **목록에는 이유와 함께 남는다**:
   - 수요 근거 2건 이상(서로 다른 글), 출처 2종 이상
   - 데이터 기간 2주 이상(모자라면 "잠정")
   - 재료 오픈소스 중 허용 라이선스 1개 이상(재료가 있는 경우)
   - `criteria` 제외 분야 아님
3. **평가표**(sol high, 1번과 같은 호출에서 함께 받아 호출 수를 줄인다) — 항목별 1~5점 + 한 줄 근거 + 인용:

   | 항목 | 질문 | 가중치(기본) |
   |---|---|---|
   | 수요 강도 | 구체적인 불편·요청이 있는가 | 25% |
   | 지불 의사 | 누가 돈을 내며 근거가 있는가 | 20% |
   | 시기 | 왜 지금인가 | 15% |
   | 경쟁 공백 | 경쟁 제품이 놓친 고객·기능이 있는가 | 15% |
   | 1인 실현성 | 1인 4~8주 MVP가 가능한가 | 15% |
   | 방어력 | 대형 업체가 기능 하나로 덮을 위험은? | 10% |

   최종 점수 = 가중 합(코드 계산, 5점 만점). 가중치는 설정으로 바꾼다.
4. **반대 검토**(선택, 기본 켬, sol high 새 호출): 관문을 통과한 1위 분야만 "실패할 이유 3가지와 반증 근거"로 검토한다. 치명 위험이면 점수를 깎는다. 비용을 줄이려면 끌 수 있다.
5. **결정**: 최종 점수 ≥ 의뢰 기준점(기본 3.5) 이고 치명 위험이 없으면 **개발 의뢰서**를 쓴다(sol high, 1회). 아니면 **"사업성 미달"**과 이유(가장 가까웠던 분야가 무엇이 모자랐는지)를 쓴다. 억지로 의뢰하지 않는다.
6. **심사 기록 저장** `out/analysis/<분석 ID>.json`: 분야마다 관문 결과, 평가표, 인용, 반대 검토 요지, "무엇이 바뀌면 의뢰 가능한가".

호출 수: 테마 지정 기준 **sol high 1~3회**(정리+평가 1회, 반대 검토 1회, 의뢰서 1회 — 미달이면 의뢰서 없음).

### 5-3. 분석 결과 구성

```
[사업성 분석] 로컬 소형 모델 문서 검토 외 1개 — 의뢰 1건 / 또는 사업성 미달

1. 판단: 의뢰서 요약 / "사업성 미달" + 이유 2~3줄
2. 검토 분야 점수 순 목록 (한 줄씩)
   3.8  로컬 문서 검토 설치형 도구 · 의뢰 →
   2.9  팀 위키 자동 요약         · 가장 약함: 지불 의사(2)   · [간단 보기]
   2.4  MCP 서버 모니터링         · 관문 탈락: 수요 근거 1건  · [간단 보기]
3. 개발 의뢰서 전문 (의뢰가 있을 때)
4. 사용량·비용
```

### 5-4. 개발 의뢰서 (기준 통과 시)
1. 의뢰 제목·한 줄 요약
2. 배경·왜 지금 — 리포트 수치 인용
3. 목표 고객과 문제 — 수요 근거 인용
4. 사업성 판단 — 평가표 점수·근거, 반대 검토 요지와 답변
5. MVP 범위 — 꼭 필요한 기능 3~5개 / 하지 않을 것
6. 기술 제안 — 재료 오픈소스(라이선스)·모델·API, 예상 운영비
7. 수익화 가설
8. 검증 계획 — 개발 전 1~2주 값싼 검증과 **중단 기준**
9. 일정 제안 — 주 단위(1인)
10. 완료 기준(인수 조건)
11. 위험·확인 필요

### 5-5. 간단 보기 (0원)
- 목록 항목의 [간단 보기]는 저장된 심사 기록을 그대로 보여 준다(추가 LLM 호출 없음). PC `Main --analysis-detail <분야 ID>`.
- 내용: 한 줄 요약·대상 고객, 평가표 6항목 점수+근거, 관문 결과, 반대 검토 요지, 근거 링크 최대 3개, **무엇이 바뀌면 의뢰 가능한가**.
- 이어서: [추가 질문](비용 발생, §5-1), [이 분야 지켜보기](추적 목록에 올림).

### 5-6. 내 응답과 학습
- 의뢰서 **수락** → 분야 자동 추적(★ 추적 로직 재사용), 다음 주 리포트에 "진행 중 의뢰의 시장 변화"(코드 지표만, 0원).
- **거절 + 이유**(시장 작음·이미 있음·너무 큼·내 분야 아님·근거 약함·기타) → 다음 분석 요청의 피드백 입력.
- **보류** → 4주 뒤 리포트에 다시 표시.
- 분석 요청·간단 보기·지켜보기 기록은 "관심 신호"로 리포트의 ◆ 순서에 반영(코드).

## 6. 모델 설정 (OpenAI)

| 단계 | 모델 | 추론 강도 | 언제 |
|---|---|---|---|
| ① 리포트 전체 | — | — | 코드만, 0원 |
| ① 주제 묶기(선택) | `gpt-6.2-sol` | low | 기본 꺼짐 |
| ② 기회 정리 + 평가표 | `gpt-6.2-sol` | **high** | 요청 시 |
| ② 반대 검토 | `gpt-6.2-sol` | **high** | 요청 시(끌 수 있음) |
| ② 의뢰서 | `gpt-6.2-sol` | **high** | 기준 통과 시 |
| ② 추가 질문 | `gpt-6.2-sol` | medium | 요청 시 |
| 간단 보기 | — | — | 저장분, 0원 |

- `gpt-6.2-sol`은 지금 개발 리뷰에 쓰는 Codex 실행 기록에서 확인한 이름이다. 실행할 때 OpenAI 모델 목록 API에서 sol 계열 최신을 확인해 바꿀 수 있게 설정값(`analysisModel`)으로 둔다.
- 기존 `OpenAiProvider`가 추론 강도(low·medium·high)를 이미 넘긴다. `LlmRouter`에 새 단계 `analysis`를 추가한다.
- **가격표에 `gpt-6.2-sol` 단가가 있어야 추정 비용 표시·예산 사전 예약이 동작한다**(`requirePrice`). OpenAI 공식 가격 페이지에서 확인해 넣는다(현재 미확인).
- 추론 high는 응답이 오래 걸린다. 응답 시간 제한은 10분.
- 매일 카드 파이프라인 모델(Claude 기본)은 그대로 둔다.

## 8. 구현 위치와 순서

- 모두 `core`(순수 Kotlin).
  - `collector.trend`(①): `TrendStore`, `Backfill`, `ThemeMapper`(코드 규칙 + 별칭표, LLM 선택), `TrendAnalyzer`(순수 함수), `CandidateMarker`(◆ 규칙), `TrendReportRenderer`.
  - `collector.analysis`(②): `AnalysisRequest`, `CostEstimator`, `OpportunityAnalyzer`(정리+평가표), `ViabilityGate`, `Critic`, `DevRequestWriter`, `AnalysisValidator`(인용·수치 대조), `AnalysisStore`, `AnalysisRenderer`, `AnalysisDetailRenderer`.
- 프롬프트(사용자 수정 가능): `analysis-opportunity`(정리+평가), `analysis-critic`, `analysis-request`(의뢰서), `analysis-ask`(추가 질문), 선택 `trend-themes`.
- PC 실행: `Main --trend`(리포트), `--backfill 4w`, `--analyze …`, `--ask …`, `--analysis-detail …`.
- 타입(초안): `TrendRow`, `TrendReport`, `Theme`, `AnalysisRequest`, `Opportunity`, `GateResult`, `ViabilityScore`, `CriticReview`, `AnalysisDecision`(REQUEST / NOT_VIABLE + 이유), `DevRequest`, `AnalysisRun`, `DevRequestResponse`.

| 단계 | 내용 | LLM 비용 | 완료 확인 |
|---|---|---|---|
| S1 | 일별 집계·재등장·스냅샷 보강 + 코드 주제 묶기 + `TrendAnalyzer` + ◆ 규칙 + 리포트(HTML/텍스트) | 0 | 2일치 + 테스트 데이터로 리포트 출력 |
| S2 | 과거 채우기(HN·GitHub 4주) | 소액(선택) | 4주 트렌드 표 확인 |
| S3 | `analysis` 단계·sol 가격표·추정 비용 확인 + 테마 지정 분석(정리+평가+관문+결정) + 심사 기록 + 간단 보기 | 요청 1회 | 실제 요청 1건 결과 확인 |
| S4 | 반대 검토 + 의뢰서 + 전체 분석 + 추가 질문 | 요청 1~2회 | 의뢰서 1건 실물 확인 |
| S5 | 응답 루프 + 리포트 메일 발송 + 앱 화면 설계(SC 추가) | 0 | 응답 반영 테스트 |

진행 방식은 기존과 같다: Codex 개발 + 두 모델 동시 리뷰, 최대 5회.

## 9. 결정

**정해진 것**
- 기술 분석은 자동 리포트(코드, 0원). 사업성 분석은 **요청할 때만**(v3).
- 분석 결과에서 사업성 낮은 분야는 점수 순 한 줄 목록, 상세는 간단 보기(0원)(v2).
- LLM은 OpenAI, 분석 모델 `gpt-6.2-sol`, 추론 high(v2).

**남은 것**
1. 리포트 주기 — 주 1회(기본 일요일)?
2. 의뢰 기준점 — 기본 3.5/5.
3. **내 기준(`criteria.default.md`)** — 사업성 분석의 기준이라 품질을 가장 크게 좌우한다. 아직 비어 있음.
4. 과거 채우기 — 분류까지(소액) / 태그 집계만(0원) / 안 함.
5. 분석 예산 — 요청 1건 상한·월 상한(sol 단가 확인 후).
6. 반대 검토 기본값 — 켬(정확도) / 끔(비용).
7. 의뢰서 깊이 — 11개 항목 / 1페이지 요약 + 요청 시 상세.
