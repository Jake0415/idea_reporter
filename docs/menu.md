## 1. Horizon 데모 분석 (2026-11-19 브리핑)

[Horizon 데모](https://thysrael.github.io/Horizon/) 2026-11-19 브리핑을 확인했다. 최근 브리핑은 중국어만 공개된다(영어판은 2026-07-30까지). 각 행의 근거는 REA 검증 보고서 [verification/horizon-rea-check.md](verification/horizon-rea-check.md)에 있다.

결정 열의 뜻: **차용** = 같은 방식으로 씀 / **변형** = 아이디어는 가져오되 형태를 바꿈 / **우리 결정** = Horizon과 무관하거나 반대.

| 관찰 | 실제 모습 | 우리 결정 |
|---|---|---|
| 상단 단계별 건수 | "43건 중 11건을 골랐다" 한 줄 (전체 → 선택 2단계) | **차용.** "수집 412 → 후보 18 → 카드 5" (SC-01, 메일). 3단계는 우리 확장 |
| 목차 | 프로필별 묶음, 제목 + 점수 배지 | **차용.** 카드 목록에 분류·점수·배지 |
| 제목 | 원문 제목이 아니라 사실을 요약한 문장 | **차용.** 카드 제목은 "누구의 무엇을 푸는가"가 드러나게 |
| 첫 블록 | 제목 바로 아래 요약 문단(블록 제목 없음) | **차용.** 카드 상세 첫 줄 = 한 줄 설명 |
| 출처 줄 | 요약 다음 줄에 출처 · 작성자 · 시각 · "커뮤니티 토론" 링크. 토론 링크는 토론 페이지가 따로 있는 출처(HN 등)에만 붙음 | **차용.** 근거 항목마다 출처·시각·원문 링크, 토론 링크는 HN·Reddit 근거에만 |
| 배경 블록 | 배경 블록 **안에서** "10월 29일 브리핑에서 보도했던…"처럼 과거 브리핑을 날짜로 인용(최대 2건, 직접 연결된 것만) | **변형.** 별도 "과거 언급" 블록으로 분리(과거 기록 검색). "직접 연결만, 회사·분야만 같으면 버림" 규칙은 차용 |
| 영향 블록 | "누구에게 무슨 영향" 실무 관점 | **변형.** "실행 판단" 블록(난이도·차별화·위험·검증) |
| 커뮤니티 블록 | 댓글 작성자를 이름으로 인용, 찬반 의견을 함께 | **차용.** 사람들의 요청·불편 블록에 댓글 인용(찬반 포함) |
| 불확실성 표시 | "커뮤니티 주장, 공식 자료로 확인 안 됨", "업체 주장"을 **본문 문장으로** 명시(별도 표시 없음) | **변형.** 본문에도 같은 식으로 쓰고, 별도 "확인 필요" 블록(`caveats`)을 둠 |
| 태그 | 항목 끝에 태그 3~5개 (1차 분석 단계에서 생성) | **차용.** 1차 분류에서 생성, 보관함 검색·필터에 사용 |
| 참고 링크 | 접힌 목록. 도구 결과로 검증된 출처만, 도구 인용이 없으면 목록 자체가 없음 | **차용.** 근거 링크 블록, 앱에서도 기본 접힘 |
| 블록 제목 | 블록 종류는 고정이지만 제목은 LLM이 항목마다 다르게 씀(「影响与处置」, 「此前进展」 등) | **변형.** 앱 화면이므로 블록 제목은 고정 |
| 묶음 | 기술 뉴스·기술 블로그·금융 뉴스가 한 페이지에 섞임 | **우리는 AI 아이디어만.** 프로필은 근거 구분용이고 카드는 하나의 목록 |
| 한계 | 같은 사건만 하나로 합침(중복 항목의 본문·댓글을 대표에 붙임). 여러 근거를 엮어 "그래서 무엇을 만들까"를 내는 종합은 없음. 피드백·보관함 필터 없음 | **우리 고유 기능:** 근거 종합 카드, ★·관심 없음, 반복 주제 |

## 3. 메뉴 구조

```
SC-00 첫 실행 설정 (최초 1회: API 키 → 메일 → 내 기준 → 첫 실행)

하단 탭
├── ① 오늘
│   ├── SC-01 오늘의 카드 (맨 위: 추적 줄)
│   └── SC-02 카드 상세
├── ② 추적
│   ├── SC-13 추적 목록
│   └── SC-14 추적 상세
├── ③ 보관함
│   ├── SC-03 지난 카드
│   └── SC-04 반복 주제            (L)
├── (수집함)
│   └── SC-05 오늘 수집 항목       (L, MVP에서는 설정 안으로)
└── ④ 설정
    ├── 수집
    │   ├── SC-07 출처 관리 (+ SC-07a 출처 상세)
    │   └── SC-08 분류 기준      (L)
    ├── AI
    │   ├── SC-11 AI 공급자·모델
    │   └── SC-15 프롬프트 (+ SC-16 프롬프트 편집)
    ├── 아이디어
    │   └── SC-09 내 기준·카드 구성
    ├── 운영
    │   ├── SC-10 실행 기록 (+ SC-10a 실행 상세)
    │   └── SC-11 일정·메일·API 키·모델·백업
    └── 정보 (버전, 오픈소스 고지)

진입 경로
- 실행 완료 알림 → SC-01
- 추적 업데이트 알림 → SC-14
- 실행 실패 알림 → SC-10a
- 메일의 카드 링크 → 앱 링크 `ideacollector://card/{cardId}` → SC-02
- 메일의 추적 링크 → `ideacollector://track/{trackedId}` → SC-14
```

MVP의 하단 탭은 **오늘·추적·보관함·설정** 4개(아이콘만, 디자인 A 피드). 수집함은 화면만 나중이고, 탈락 이유 기록은 1단계부터 core에 넣는다.

## 4. 화면 명세

### SC-00 첫 실행 설정
- **목적:** 처음 한 번 필요한 값만 받고 첫 실행까지 안내.
- **단계:** ① AI 공급자 키 — Claude(Anthropic)·OpenAI 중 하나 이상(입력하면 바로 모델 목록 호출로 확인, 끝 4자리만 표시) + GitHub 토큰(선택) → ② 받는 메일 주소, 발송 계정(Gmail 앱 비밀번호) + [테스트 발송] → ③ 내 기준 4문항(SC-09와 같은 양식, 건너뛰면 기본값) → ④ [지금 첫 실행].
- **상태:** 키 검증 실패 시 해당 단계에서 멈추고 이유 표시.
- **데이터:** SecretProvider, Mailer, `criteria`.

### SC-01 오늘의 카드
- **목적:** 오늘 받을 것을 한눈에.
- **표시:**
  - **추적 줄(맨 위):** 추적 중인 아이디어를 원형 아이콘으로 가로 나열(인스타그램 스토리 형태). 오늘 새 업데이트가 있으면 accent 고리 + 위쪽에 정렬, 없으면 회색 고리. 누르면 SC-14. 추적이 없으면 "★를 누르면 여기서 계속 추적합니다" 안내.
  - 상단 단계별 건수: "수집 412 → 후보 18 → 카드 5", 마지막 실행 시각, 오늘 비용. 실패 출처가 있으면 "Reddit 수집 실패" 띠(누르면 SC-10a).
  - 카드 목록(최대 `ideaCount`): 제목, 한 줄 설명, 분류(고정 10개 중 하나), 배지(여러 곳에서 화제·연속 등장·급상승 — 코드가 계산, design.md §7-1 ⑤), ★ 버튼.
- **동작:** 카드 누르기 → SC-02, ★ 토글, [지금 실행](실행 중이면 진행 단계 표시·버튼 비활성), 아래로 당겨 새로고침(저장된 결과 다시 읽기).
- **같은 날 다시 실행:** 오늘의 카드를 새 결과로 교체한다(이전 결과는 SC-10에 남음). 메일은 하루 1회만 자동 발송. 실행 전 확인 창: "오늘 카드를 새 결과로 바꿉니다".
- **상태:** 아직 오늘 실행 전 → 어제 카드 + "다음 실행 예정 07:00"; 실행 중 → 단계 표시(수집 중/분류 중/작성 중); 예산 초과로 일부만 생성 → 안내 띠.
- **데이터:** IdeaStore(오늘 카드), RunReport(단계별 건수·비용·실패 출처), FeedbackStore.

### SC-02 카드 상세
- **목적:** 아이디어를 판단하는 데 필요한 근거를 한 화면에.
- **블록 구성:** §5 참고.
- **동작:** ★, 관심 없음(이유: 이미 있음 / 너무 큼 / 내 분야 아님 / 근거 약함 / 기타 입력 — 반영 방식은 design.md §7-1 ⑧), 근거 원문 열기(브라우저), (L) 메모, 공유, 더 파고들기.
- **데이터:** IdeaCard, SignalRef → Item, FeedbackStore, HistorySearch.

### SC-13 추적 목록
- **목적:** ★한 아이디어가 그 뒤로 어떻게 변하는지 한곳에서 본다.
- **표시:** 추적 아이디어 목록(최대 `maxTracked` 10개). 줄마다 제목, 분류, 추적 시작일, 마지막 업데이트("오늘 새 소식 3건" / "5일 전"), **관련 글 수 화살표**(상승·유지·하락), 상태(추적 중 / 조용함 — 30일 새 소식 없음). 정렬: 오늘 업데이트 있는 것 → 최근 업데이트순.
- **동작:** 줄 누르기 → SC-14, 밀어서 추적 종료(확인: "추적을 멈출까요? 기록은 남습니다"), 상단 "추적 한도 7/10".
- **상태:** 추적 없음(안내 + 오늘 탭으로), 한도 도달(새 ★ 시 "가장 오래 조용한 것을 멈출까요?").
- **데이터:** TrackedStore(TrackedIdea), TrackingUpdate 최신 1건.

### SC-14 추적 상세
- **목적:** 한 아이디어의 변화 기록과 지금 상태를 본다.
- **표시:**
  - 머리: 제목, 분류, 추적 시작일, 관련 글 수 점수와 7일 추이(작은 막대), 상태.
  - **달라진 점 타임라인:** 날짜별 업데이트 카드 — 요약 한두 문장 + 변화 종류 칩(새 이미 나온 제품 / 수요 증가 / 수요 감소 / 기술 새 버전 / 위험 변화) + 근거 링크(수집 항목만).
  - 이미 나온 제품 목록(추적 중 발견된 것 누적).
  - 원래 카드 보기(SC-02 링크).
  - 추적 키워드: 자동 추출된 키워드 칩(제목 핵심어·태그·주제 키·이미 나온 제품명) — 추가·삭제 가능.
  - (L) 주간 심층 조사 결과.
- **동작:** 키워드 편집, 추적 종료, 원래 카드 열기, 근거 원문 열기.
- **상태:** 아직 업데이트 없음("내일부터 조사합니다"), 조용함, 종료됨(읽기 전용).
- **데이터:** TrackedIdea, TrackingUpdate 목록, IdeaCard, Item.

### SC-15 프롬프트
- **목적:** AI에게 주는 지시문을 사용자가 직접 보고 고칠 수 있게 한다. 처음에는 기본 프롬프트(AI가 작성)로 동작한다.
- **표시:** 단계별 묶음 — ① 1차 분류(`classify`) ② 분류 기준 3종 × (포함 기준 `match`, 평가표 `analysis`) ③ 카드 작성(`ideas`) ④ 추적 업데이트(`track`) ⑤ 내 기준(`criteria`). 줄마다 이름, 쓰는 단계·모델, 상태(기본값 / **수정됨** / 기본값 새로 바뀜), 마지막 수정일.
- **동작:** 줄 누르기 → SC-16. 상단 "수정한 프롬프트 2개 · 모두 기본값으로" (확인 필요).
- **데이터:** PromptStore(기본값=앱 리소스, 사용자 수정본=기기 저장소).

### SC-16 프롬프트 편집
- **목적:** 프롬프트 하나를 안전하게 고친다.
- **표시:**
  - 머리: 이름, 쓰는 단계·모델, 상태, 버전(v3 · 11/19 수정).
  - 안내 띠: "출력 형식(JSON)과 인용 검증은 코드가 강제합니다. 여기서는 판단 기준과 글쓰기 규칙을 바꿉니다."
  - 편집기: 고정폭 글꼴, 줄 번호, 글자 수(상한 20,000자).
  - 입력 설명(읽기 전용): 이 프롬프트가 받는 데이터(예: items, recentTopics, tracked)와 출력 필드.
- **동작:** 저장(새 버전), 기본값으로 되돌리기, **기본값과 비교**(바뀐 줄 표시), **버전 기록**(최근 10개, 복원), **시험 실행**(최근 실행 자료에서 5건으로 돌려 결과와 비용 표시 — 저장 전 확인용, 비용은 일일 예산에 포함), 저장하지 않고 나가면 확인.
- **상태:** 기본값 사용 중, 수정됨, 기본값 새로 바뀜(앱 업데이트로 기본값이 바뀌었는데 사용자 수정본이 있을 때 → 비교 후 "내 수정 유지 / 새 기본값으로"), 시험 실행 중·결과, 검증 실패(빈 내용·상한 초과).
- **데이터:** PromptStore, PromptVersion, LlmRouter(시험 실행).

### SC-03 지난 카드
- **표시:** 날짜별 묶음 목록(날짜 머리글에 그날 단계별 건수 요약), 카드 줄은 SC-01과 같은 모양.
- **필터:** ★만, 분류, 태그, 글자 검색(제목·설명·태그 전문 검색), 관심 없음 숨기기(기본 켬).
- **데이터:** IdeaStore, FeedbackStore, HistorySearch(FTS).

### SC-04 반복 주제 (L)
- **표시:** 최근 30일 동안 여러 번 나온 주제(`topicKey`, 날짜를 넘어 같은 키 재사용) 목록: 주제명(`topicLabel`), 등장 횟수, 첫·마지막 날짜, 관련 카드 수, 흐름(작은 막대).
- **동작:** 주제 누르기 → 관련 항목·카드 목록.
- **데이터:** ItemStore(topicKey 이력), IdeaStore.

### SC-05 오늘 수집 항목 (L)
- **표시:** 출처별 탭, 항목마다 제목·출처 점수·통과 여부·탈락 이유(`DropReason`)·분류 점수와 이유.
- **동작:** 탈락 항목에 "다음엔 포함" 표시 → 출처 기준 점수 조정 참고용 기록. 원문 열기.
- **데이터:** ItemStore(오늘 항목 + DropReason + ClassifiedItem).

### SC-07 출처 관리
- **표시:** 출처 목록: 이름, 켜짐 여부, 기본 프로필, 최근 30일 통계(하루 평균 수집, 통과율, 평균 점수), 마지막 실패 시각.
- **SC-07a 출처 상세:** 검색어(여러 개), 출처별 최소 점수, 최대 건수, 기간, 프로필 배정(명시/후보), [연결 테스트](실제 호출 1회, 건수와 첫 3건 제목 표시), [기본값으로 되돌리기].
- **(L)** RSS 피드 추가: 이름, URL, 프로필, 최대 건수.
- **데이터:** SourceConfig(Room에 덮어쓰기), SourceStats.

### SC-08 분류 기준 (L)
- **표시:** 쓸 수 있는 기술·사람들의 요청·불편·이미 나온 제품 3개: 기준 점수(0~10), 후보 상한, 평가표 요약.
- **동작:** 기준 점수·상한 수정, 평가표(`analysis.md`) 보기, 고급: 평가표 직접 수정(되돌리기 제공).
- **데이터:** ProfileConfig.

### SC-09 내 기준·카드 구성
- **내 기준:** 개발 범위(1인/소수, 기간), 대상 고객(개발자·B2B·소비자 등 복수 선택 + 메모), 관심 분야, 제외 분야, 수익화 방식. 저장 시 `criteria` 텍스트로 변환해 아이디어 작성 프롬프트에 넣음.
- **카드 구성:** 하루 카드 수(3~7), 분류별 최대 개수(분류 목록은 고정 10개), 같은 대표 태그 후보 최대 개수, 최근 피드백 반영 개수.
- **데이터:** `criteria`, PipelineConfig.

### SC-10 실행 기록
- **표시:** 날짜별 실행: 결과(성공/일부/실패), 단계별 건수, 비용, 소요 시간. 상단에 이번 달 비용 합계와 예산 대비.
- **SC-10a 실행 상세:** 단계별 입력/출력 건수와 소요 시간, 출처별 수집 결과와 실패 이유, LLM 호출별 공급자·모델·토큰·비용·대체 공급자 사용 여부, 인용 검증에서 제거된 근거 수.
- **데이터:** RunReport.

### SC-11 일정·메일·API 키·모델·백업
- **일정:** 실행 시각, Wi-Fi에서만, 충전 중에만, 배터리 최적화 예외 안내(제조사별 설정 화면 이동).
- **메일:** 받는 주소, 발송 계정, [테스트 발송], 메일 받기 끄기.
- **AI 공급자 키:** Claude(Anthropic), OpenAI 각각 상태(연결됨 / 확인 실패 / 없음), 끝 4자리, 마지막 확인 시각. [등록·교체], [다시 확인], [삭제]. 하나 이상 연결돼 있어야 실행된다. 확인 실패(키 만료·폐기)면 오늘 탭과 알림에 안내.
- **출처 키:** GitHub, Reddit, Product Hunt — 저장 여부만 표시(값은 다시 보여주지 않음), 교체·삭제.
- **모델:** 단계별(분류 / 카드 작성)로 공급자와 모델을 고른다. 모델 목록은 연결된 공급자에서 받아 온다. "대체 공급자 사용"(두 키가 모두 있을 때), 일일 예산, 모델별 가격표(공급자 가격이 바뀌면 고칠 수 있음, 비용은 "추정"으로 표시).
- **(L) 보충 검색:** 켜기와 횟수, 사용할 공급자.
- **(L) 백업:** 설정·카드·피드백 JSON 내보내기/가져오기 (키는 제외).

## 5. 카드 상세 블록 구성

Horizon의 "첫 블록 + 필수 블록 + 선택 블록" 방식을 따른다(차용). 내용이 없는 선택 블록은 숨기고, 필수 블록이 빠진 카드는 거부한다.

Horizon과 다른 점(변형):
- 블록 제목은 고정이다(Horizon은 LLM이 항목마다 씀).
- 6 과거 언급과 8 확인 필요는 Horizon에서는 다른 블록 안의 문장이다. 우리는 별도 블록으로 뺐다. 본문에서도 "업체 주장", "커뮤니티 주장"은 문장으로 밝힌다.
- 9 근거 링크는 기본 접힘으로 보여준다.

| 순서 | 블록 | 필수 | 내용 | IdeaCard 필드 |
|---|---|---|---|---|
| 0 | 머리 | 필수 | 제목, 한 줄 설명(블록 제목 없이), 분류, 배지, 태그 | title, oneLiner, category, badges |
| 1 | 오늘 고른 이유 | 필수 | 왜 오늘 이 카드인가 한두 문장 | whyToday |
| 2 | 문제 | 필수 | 누구의 어떤 불편 | problem |
| 3 | 쓸 수 있는 기술 | 필수 | 가능하게 한 기술: 제목·출처·점수·라이선스, 원문 링크 | techSignals |
| 4 | 사람들의 요청·불편 | 선택 | 불편·요청 근거, **댓글 인용(작성자·찬반)** | demandSignals |
| 5 | 이미 나온 제품 | 선택 | 이미 나온 것과 빈틈(불만 댓글) | competitors |
| 6 | 과거 언급 | 선택 | "11월 13일 카드/항목에서…" 날짜 인용 최대 2개 | history |
| 7 | 실행 판단 | 필수 | 난이도(1인 기간), 차별화, 가장 큰 위험 1개, 2주 검증 방법 | effort, differentiation, biggestRisk, validationPlan |
| 8 | 확인 필요 | 선택 | 근거가 한 출처뿐, 업체 주장, 커뮤니티 주장 등 | caveats |
| 9 | 근거 링크 | 필수 | 이번 실행에서 수집된 항목 URL만(인용 검증 통과분) | 모든 SignalRef |

규칙: 쓸 수 있는 기술 1개 이상 + (사람들의 요청·불편 또는 이미 나온 제품) 1개 이상이 없는 카드는 만들지 않는다. 블록별 인용 대상: 쓸 수 있는 기술 = tech-signal 항목, 사람들의 요청·불편 = demand-signal 항목, 이미 나온 제품 = market-signal 또는 tech-signal 항목(같은 일을 하는 기존 오픈소스 포함). 같은 항목을 기술과 요청·불편/이미 나온 제품에 동시에 쓰면 무효. 인용은 카드 작성에 넘긴 후보(와 합쳐진 URL)만.

## 6. 메일 리포트

```
제목: [AI 아이디어] 11월 19일 — 카드 5개 (수집 412 → 후보 18)

1. 머리      날짜, 단계별 건수 한 줄, 실패 출처 있으면 한 줄 경고
2. 목차      카드 5개: 번호 · 제목 · 분류 · 배지
3. 카드      카드마다: 제목 / 한 줄 설명 / 오늘 고른 이유 /
             핵심 근거 2개(링크) / 가장 큰 위험 / [앱에서 보기] 링크
4. 추적 업데이트  오늘 새 소식이 있는 추적 아이디어만: 제목 · 관련 글 수 화살표 ·
             달라진 점 한 줄 · [앱에서 보기](ideacollector://track/{id})
5. 반복 주제  (L) 이번 주 계속 나오는 주제 3개
5. 꼬리      오늘 비용 · 이번 달 합계 · 실행 시간
```

- 메일은 **요약본**이고, 판단은 앱(SC-02)에서 한다. 피드백 버튼은 메일에 넣지 않는다(서버가 없으므로).
- 요약본 메일, 제목의 카드 수·단계별 건수, 꼬리의 비용·실행 시간은 **우리 결정**이다. Horizon은 브리핑 전체를 메일로 보내고 제목은 날짜만 쓴다.
- 점수·분류 배지는 메일에서 JS를 쓸 수 없으므로 HTML 인라인 스타일로 직접 그린다(Horizon 메일은 `⭐️ 8.0/10` 글자 그대로).
- HTML + 일반 텍스트 둘 다 만든다(Horizon과 같음).

## 8. 남은 결정
- 내 기준 4문항의 실제 내용(SC-09 기본값) — 사용자 입력 대기.
- 실행 실패 알림을 매번 보낼지, 연속 2회 실패 때만 보낼지.
- 화면 디자인(색·글꼴·와이어프레임)은 4~5단계에서 `ui-ux-pro-max` 스킬로 진행.
